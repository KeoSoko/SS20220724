## Causes, publication evidence, and safe interpretation

- All 14 renewal transactions carried `invoice_action` metadata without a user or subscription field. Live transaction verification exposed the plan code, and the detailed provider subscription's paid invoice gave the definitive transaction relationship. The deployed webhook emitted `untracked_paystack_charge_rejected: missing_authoritative_subscription_relationship` and, in a separate user-resolved path, `renewal_reconciliation_unresolved: missing_plan_identity` for **all 14**. These are local processing failures, not failed Paystack charges.
- The five-minute orphan monitor checks for a ledger reference, not merely a resolved subscription or invoice webhook. Missing ledger rows therefore triggered 14 alerts; every alert event had a **null user ID** and the misleading classification `payment_without_provider_subscription_identity`. The direct transaction payload lacks a subscription field even though a paid provider invoice links it to an existing subscription. The alert email's generic “no subscription was created” and blind `/api/admin/payments/reconcile` suggestion are unsafe descriptions for a renewal.
- For the named payment, a user-linked `renewal_reconciliation_unresolved` event with `transactionReference` existed at **Sep 27 17:15:19**; the orphan alert was inserted at **17:22:37** with a null user. The current workspace's three-key reference-correlation query resolves user **376** on that production dataset. Thus the correlation fix was **not operating in that live alert**. A successful public autoscale deployment exists, but the deployment metadata did not provide a build revision; an older deployed build versus a divergent live path could not be conclusively distinguished. The live shadow-observation path did run for three other references; that does not establish that every renewal-boundary fix or an automatic settlement path is published.
- Deployment logs on Sep 26–27 show repeated `Connection terminated due to connection timeout` and `timeout exceeded when trying to connect` across reconciliation, deferred replay and other workers. No matching timeout was found in the sampled **Sep 27 17:14–17:24** named-reference sequence. Pool pressure is real, but assigning it as the cause of a particular missed R49 settlement would be speculation. No overlap-skip or pool-telemetry markers were found in the queried window; absence of a marker is not proof of whether a guard was deployed.
- Four missing rows are **conditional** strict-preview candidates: one exact billing boundary and three short drifts requiring explicit reviewed-boundary authorization. Eight missing rows require manual review. For any eventual authorized settlement, reverify the live transaction and exact **single paid invoice**, canonical owner, active identity count, prior payment references and invoice-period overlaps immediately before writing; require an idempotent ledger claim and linked audit event. The proposed invoice-period-end timestamps in the table differ by one second from Paystack's next-payment timestamps; confirm the application's intended entitlement convention before using them. **Do not directly apply this table as SQL.**

**Evidence limits and handling:** Production read-only SQL, live Paystack list/verify/customer/subscription GET calls, and deployed logs were used. The production read replica contained the named webhook events within seconds of the provider charge, strongly tying it to the deployed app's data. The literal email from the earlier user message was not available in the accessible task context; only a non-disclosing provider-email-to-user-376-email equality check was possible. Enumeration covers this live Paystack account through the snapshot, not another account or later payments. No credentials, card details, full sensitive provider payloads, provider mutations, production writes, settlement, charges, subscription creation, or deployment were involved.
