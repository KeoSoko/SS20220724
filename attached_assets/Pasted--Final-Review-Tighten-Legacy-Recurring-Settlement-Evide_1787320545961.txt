# Final Review — Tighten Legacy Recurring Settlement Evidence

The proposed Task #59 implementation is broadly approved, but one condition must be tightened before deployment.

Do not deploy yet.

## 1. Do not equate subscription activation with recurring settlement

The helper:

`hasSuccessfulRecurringSettlementEvidence`

must not treat every:

`subscription_activated`

event as proof of a successful recurring renewal.

A first/customer-initiated subscription payment may also create `subscription_activated`.

That would incorrectly recreate:

`initial payment succeeded → assume recurring relationship is healthy`

which is the billing assumption we have specifically removed.

## 2. Define authoritative recurring settlement evidence

Determine what existing local/provider evidence distinguishes:

### Initial/customer-initiated checkout

from:

### Subsequent Paystack recurring `charge.success`

Prefer explicit authoritative signals such as:

* Paystack webhook with subscription context;
* `subscription_code`;
* provider invoice/renewal context;
* provider-originated recurring transaction source;
* event metadata proving it was a renewal;
* transaction occurring against an already-existing subscription cycle.

Do not rely only on the generic event name:

`subscription_activated`

## 3. Jesse must still qualify

JesseSoko25 has five consecutive successful provider renewal cycles through the legacy webhook path.

Confirm that the strengthened evidence rule still classifies Jesse as:

`subscription_active`

without requiring a new checkout.

## 5. Recurring-payment regression

Expected:

`subscription_active`

## 6. Identity recovery — verify exact plan too

* exact subscription code;

* no competing active identity.

Do not recover an identity based only on:

`customer_code + exactly one active local subscription`

if provider plan evidence contradicts the local plan.
