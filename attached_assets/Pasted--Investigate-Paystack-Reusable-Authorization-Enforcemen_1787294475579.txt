# 1. Paystack contract we need to enforce

Paystack's documentation establishes two separate concepts:

### Successful initial payment

A successful first payment proves the payment itself succeeded.

It does NOT by itself prove that the payment instrument can be used for future recurring debits.

### Reusable authorization

Paystack states that only payment instruments where:

```text
authorization.reusable === true
```

can be charged recurrently.

If `authorization.reusable` is not explicitly `true`, Simple Slips must not treat that authorization as recurring-ready.

Paystack also recommends that applications requiring recurring charges restrict initial payment to payment channels that support reusable authorizations.

This distinction must be treated as a billing invariant:

```text
payment_success != recurring_ready
```

and:

```text
recurring_ready requires authorization.reusable === true
```

# 7. Subscription creation timing

This is particularly important.

Determine whether Paystack creates the `SUB_*` automatically because Simple Slips sends:

```text
plan: PLN_...
```

during transaction initialization.

If so, determine whether Simple Slips can know:

```text
authorization.reusable
```

BEFORE Paystack has already created the subscription.

If Paystack creates the subscription as part of the initial plan checkout before Simple Slips can verify authorization reusability, document that architectural limitation clearly.

We need to know whether the correct future design should instead be:

```text
1. collect/verify reusable payment method
2. verify authorization.reusable === true
3. only then establish recurring subscription
```

rather than:

```text
1. initialize transaction with plan
2. Paystack automatically creates subscription
3. discover afterward that authorization cannot renew
```

Do NOT change architecture yet.
