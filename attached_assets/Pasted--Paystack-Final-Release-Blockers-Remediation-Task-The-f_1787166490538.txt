# Blocker 1 — Untracked initial charge can masquerade as recurring

The current webhook logic can apparently classify an untracked transaction as recurring based on:

`metadata.invoice_action`

This is client-controlled metadata and must **never** be authoritative evidence that a transaction is a legitimate recurring Paystack renewal.

Fix this boundary.

## Required rule

An initial Paystack charge that does not correspond to a tracked server-owned checkout attempt must never grant entitlement merely because metadata claims it is recurring.

Recurring processing must require authoritative provider-side evidence.

For a recurring renewal, require an already-established relationship to the expected Paystack subscription identity.

At minimum, determine from the actual Paystack API/webhook structure what authoritative fields identify:

* the Paystack subscription;
* the Paystack invoice;
* the Paystack customer;
* the transaction;
* the existing local `SUB_*` identity.

Do not trust client-controlled metadata to establish this relationship.

The preferred security boundary is conceptually:

`verified Paystack transaction`

`→ tracked initial checkout attempt?`

YES:

`→ initial subscription settlement path`

NO:

`→ does authoritative provider data prove this belongs to an already-known active SUB_* identity?`

YES:

`→ recurring renewal path`

NO:

`→ reject/quarantine for manual review`

An unknown `SUB_*` arriving with an untracked transaction must not automatically establish itself as trusted and grant entitlement.

# Blocker 2 — Renewal/checkout settlement race

The audit identified this sequence:

1. Checkout attempt is pending.
2. Checkout settlement begins Paystack verification.
3. Verification occurs outside entitlement lock `36`.
4. Recurring renewal acquires lock `36`.
5. Renewal settles.
6. Renewal cancels the pending checkout.
7. Checkout verification finishes.
8. Checkout acquires lock `36`.
9. Checkout uses the stale previously-read `pending` state.
10. Distinct checkout payment can still be applied.

Fix this.

## Required rule

The checkout attempt's authoritative state must be revalidated **inside the same protected transaction/locking boundary immediately before entitlement/payment mutation**.

After acquiring the entitlement lock:

* re-read the checkout attempt;
* row-lock it if appropriate;
* verify it still exists;
* verify its reference is unchanged;
* verify it is still in an allowed settlement state;
* verify immutable terms still match;
* reject settlement if another billing operation has cancelled, failed, expired, superseded, or otherwise invalidated the attempt.

Never rely on attempt status loaded before an external Paystack verification call.

Conceptually:

`load attempt`

`→ verify Paystack externally`

`→ acquire billing-owner entitlement lock`

`→ BEGIN DB transaction`

`→ SELECT checkout attempt again / lock row`

`→ validate CURRENT state`

`→ validate verified settlement against immutable terms`

`→ write payment + entitlement + attempt completion atomically`

If current state no longer permits settlement:

**do not apply entitlement.**

Record the event for manual review because the provider may have successfully collected money.

Do not silently discard a genuinely successful Paystack charge.

# Blocker 3 — Same-reference Paystack popup behaviour

The audit established that multiple tabs can receive the same server-owned reference and potentially both invoke:

`PaystackPop.checkout()`

Do not assume Paystack makes this safe.

Investigate the existing frontend lifecycle and implement a server-controlled guard if necessary.

Our invariant is stronger than:

**one reference per intended purchase**

We ultimately need:

**one intended purchase must not expose the customer to multiple successful charges.**

Determine whether multiple Paystack checkout initialisations using the exact same reference can result in more than one successful provider transaction.

Use authoritative Paystack behaviour/documentation if available.

If this cannot be proven safe, implement an additional mechanism so that only the currently valid server checkout lease can be used to initialise/open Paystack.

Do not create a new reference merely to solve this problem.

Do not weaken retry/lost-response recovery.

Report exactly what protection is implemented and why it prevents duplicate charging.
