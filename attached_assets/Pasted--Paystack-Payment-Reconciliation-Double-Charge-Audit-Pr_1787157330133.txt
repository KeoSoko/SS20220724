I need you to perform a **full audit of the Paystack payment, subscription, webhook, reconciliation, retry, and account-status logic in Simple Slips**.

This is a **production billing system with real paying customers**, so do **NOT make any code changes yet**.

Your first job is to investigate the current implementation, trace the complete payment lifecycle, identify every scenario that could cause:

* a customer to be charged twice;
* the same Paystack transaction to be recorded twice;
* duplicate subscriptions to be created;
* a successful payment to be treated as unpaid;
* an unsuccessful payment to incorrectly activate access;
* a webhook and frontend callback both processing the same payment;
* retries creating additional charges;
* subscription renewals being duplicated;
* reconciliation jobs incorrectly generating or modifying payments;
* stale or delayed Paystack webhooks changing a newer subscription state;
* team/workspace users being charged when billing should belong to the workspace owner;
* an existing active subscriber being sent through checkout again;
* multiple concurrent payment requests for the same user;
* a payment succeeding on Paystack but Simple Slips not recognising it;
* the database and Paystack disagreeing about the customer's subscription state.

## Phase 3 — Audit Idempotency

This is extremely important.

For every payment-related endpoint and webhook handler, determine:

**What happens if the exact same request/event is received twice?**

Paystack may resend webhooks. Browsers may retry requests. Users may double-click buttons. Network requests may time out even when the original request succeeded.

Audit whether we have proper idempotency around:

* transaction references;
* Paystack transaction IDs;
* webhook events;
* subscription codes;
* invoice/payment records;
* renewal events;
* reconciliation jobs.

Look specifically for patterns like:

```python
payment = Payment(...)
db.add(payment)
```

without first checking whether that Paystack transaction/reference has already been processed.

I want database-level protection where appropriate, not only application-level `if` statements.

For example, investigate whether fields such as these should have UNIQUE constraints:

* Paystack transaction ID;
* Paystack reference;
* subscription code;
* event identifier where available.

Do **not** add constraints yet if production data may already contain duplicates. First inspect the data and report what migration would be safe.

## Phase 9 — Race Conditions

Look for concurrency problems.

Examples:

Two webhook requests arrive simultaneously:

```text
Webhook A checks: payment doesn't exist
Webhook B checks: payment doesn't exist
Webhook A inserts payment
Webhook B inserts payment
```

or:

```text
Request A checks user isn't subscribed
Request B checks user isn't subscribed
Both initialise Paystack transactions
```

Identify where database transactions, row locking, atomic upserts, or unique constraints are required.
