---

# 1. Root problem

The current signed `invoice.update` paid path can establish:

* exact paid invoice;
* exact transaction reference;
* exact customer email;
* exact provider subscription code;

but when:

`paystack_subscription_identities`

does not already contain that legacy `SUB_*`, the webhook stops at:

`renewal_reconciliation_unresolved`
→ `unknown_subscription_identity`

This strands a legitimate successful recurring payment.

Meanwhile the hardened `charge.success` path now has:

`attemptSafeLegacyWebhookIdentityRecovery`

for exactly this class of legacy missing-identity problem.

The paid invoice path needs equivalent guarded recovery.

---

# 2. Reuse the hardened identity-recovery mechanism

Do not build a weaker second recovery system.

Refactor/reuse the existing:

`attemptSafeLegacyWebhookIdentityRecovery`

or create one shared internal primitive used by both:

* recurring `charge.success`
* paid `invoice.update`

The same ownership and ambiguity protections must apply.

---

# 3. Required provider evidence

Automatic identity recovery from a signed paid invoice is allowed only when authoritative provider evidence establishes:

* valid signed Paystack webhook;
* invoice is actually paid;
* exact `subscription_code`;
* exact Paystack customer relationship;
* exact expected Simple Slips plan;
* exact billing owner can be resolved unambiguously;
* no competing active local identity exists;
* subscription code is not trusted by another owner;
* no local/provider ownership conflict exists.

Do not recover based solely on email.

Email may assist resolution, but stronger provider/local identifiers must validate ownership.

# 5. Multiple-subscription ambiguity

If provider evidence indicates multiple competing `SUB_*` relationships for the same customer/plan:

Do not automatically select one.

Do not:

* attach either identity;
* create checkout;
* create another subscription.

Preserve the duplicate-subscription safeguards already established.

---

# 6. Recurring readiness

Identity recovery and recurring readiness are separate.

If authoritative invoice/webhook evidence does NOT provide:

`authorization.reusable === true`

then the recovered identity must use:

`recurring_readiness = unknown`

Do not infer `ready` from:

* five successful payments;
* subscription existence;
* authorization-code existence;
* paid invoice;
* card payment method.

A legitimate recurring payment may establish identity while readiness remains `unknown`.

---

# 7. Continue settlement after safe recovery

When identity recovery succeeds:

1. create/activate the trusted local provider identity;
2. continue the existing exact renewal settlement path;
3. create the missing payment ledger row exactly once;
4. apply the paid renewal exactly once;
5. update the existing local subscription according to the normal successful-renewal rules;
6. create appropriate audit/billing events.

Do not create another local subscription if the active subscription already exists.
