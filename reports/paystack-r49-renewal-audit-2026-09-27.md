All 14 also have `untracked_paystack_charge_rejected` with `missing_authoritative_subscription_relationship`. This strongly identifies it as the relevant app production dataset. The deployment service says the public autoscale deployment has a successful build; it does not expose a build revision here. Under the current access middleware, that gives **effective premium access even when the billing date and `users.subscription_expires_at` are overdue**. Users 35 and 151 additionally inherit their effective access from workspace 148's owner, user 36, rather than from their private workspace. This is a description of present access, not proof that their independent subscription entitlements were extended.

## Why the alerts happen, and what is known about deployment

1. Every renewal payment's provider transaction metadata has `invoice_action` but no user/plan ID; the verified transaction does expose a plan code, but no direct subscription field. The webhook's generic initial-charge path records `missing_authoritative_subscription_relationship`. The separate renewal path resolves a local user and emits `missing_plan_identity`. The exact paid invoice relationship was found later by provider customer/subscription lookup; the webhook did not turn it into a local payment row. This is an **observed path**, not evidence that the payment failed.
2. The orphan monitor scans `charge.success` webhooks older than five minutes, in the most recent 24 hours, and checks only for a `payment_transactions` reference or metadata reference; it does **not** regard `renewal_reconciliation_unresolved`, invoice webhook records, or an active subscription as settled. It then creates one `orphaned_payment_alert`. The email's generic “no subscription was created” description is misleading for existing renewals. Its provider classification relies on a direct transaction subscription field that is absent in these invoices, so all 14 alerts say `payment_without_provider_subscription_identity` despite an exact linked provider invoice/subscription.
3. All 14 alert event rows have **null `user_id`**. In particular, at **Sep 27 17:15:19**, `renewal_reconciliation_unresolved` for the named reference already had `user_id=376` and `transactionReference`. The orphan alert was recorded seven minutes later at **17:22:37** with null user. Re-running the source code's intended three-key correlation as a read-only production SQL query resolves user 376. Therefore the correlation fix is **not operating for this alert**. Deployment metadata alone cannot distinguish an older published build from a divergent runtime path or unexpected query behavior. Do not claim the current workspace fix is live.
4. The live deployment does emit `legacy_renewal_shadow_observed` for Sep 18, 20 and 26 candidates and correctly flags covered member 151, showing part of the read-only preview behavior is operating. Two older alerts were settled manually. This does **not** demonstrate automatic settlement or prove every boundary fix is published. No runtime build revision was available to compare.
5. Production logs on Sep 26–27 contain repeated `Connection terminated due to connection timeout` and `timeout exceeded when trying to connect` from reconciliation, the deferred replay worker and other jobs; the latest sampled named-payment window (Sep 27 17:14–17:24) instead shows the webhook rejection, provider verification and orphan alert without a matching timeout. Pool pressure is **observed globally**, but **not proven as the cause for any individual R49 discrepancy here**. No overlap-skip or pool-telemetry markers were found in the queried log window; absence of those markers is not proof a fix is absent.

**Safety and next evidence:** Do not use the generic `/api/admin/payments/reconcile` instruction in the orphan email as a blind renewal remedy. For the four conditional candidates, obtain fresh strict settlement previews with exact customer/subscription/plan, invoice transaction ID and period, reference uniqueness, active identity count, canonical owner, and no longer or overlapping entitlement/compensation; require explicit review of each short boundary exception. For the eight manual cases, first reconcile missing intervals, old cancellation/ownership or boundary conflicts. Keep current access while evidence remains unresolved; no charge, provider mutation, production write or settlement was performed in this audit.
